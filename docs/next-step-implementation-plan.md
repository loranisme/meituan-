# Next Step — 实施计划（对齐交互方案 × 架构缺口）

本文档在已阅读的 **`Meituan_Together_updated_interactive_plan_zh.md`**（产品/交互目标）与 **`demo-open-issues-and-architecture-gaps.md`**（已知缺口）之间做对齐，并给出**分阶段、可验收**的下一步计划。

---

## 1. 双文档对齐结论

| 交互方案已定义 | 架构缺口文档指出 | 结论 |
|----------------|------------------|------|
| POI-first、Intent-first、Plan-first | Demo 仍偏 Happy Path | 需在**同一套 UI**里补**异常与降级**叙事，而非另起产品 |
| 规则层评分 + AI 层文案（5.7） | 当前仅有同步 `parseIntent` 规则 | 保持规则为真相源；**可视化「分层」**（规则标签 vs 模拟延迟/澄清）即可答辩 |
| 成局确认室状态机（6.4） | 代码里双确为定时器模拟 | 将状态机**显式化**（枚举 + UI），并增加**拒绝/过期**分支 |
| Trust Score、团购转化 | 无预授权/防鸽/退款契约 | 在确认室成功前增加 **「支付意愿锁定」Mock**，与「美团闭环」章节统一话术 |
| 地图强交互（加入局、我也想去、热度） | 部分可能未完全落地 | 对照 **§8.1 清单** 与当前 `app.js` 做 gap diff |
| 动态重规划（等位/换店） | 缺拒人→候补、鸽→退单 | 在现有 `replanMatch` 上**扩展事件类型**与 UI |

## 2. 目标优先级（建议）

### P0 — 答辩叙事与「非社交」证明

1. **成局确认室**：显式状态（`waiting_user` / `waiting_partner` / `modify` / `confirmed` / `cancelled`），避免「一键假双确」是唯一路径。
2. **履约契约 Mock**：确认流程中插入 **诚意金/预授权说明面板**（纯前端即可），成功页展示 **规则摘要一行**（核销解冻、对方退局怎么办）。
3. **拒配 / 候补**：匹配到 B 后，可演示 **B 拒绝 → 自动方案 C 或「扩大召回」文案**（数据可走 mock 队列）。

### P1 — 架构追问的「可见回答」

4. **意图分层 UI**：AI 页展示「L0 规则已解析」+ 可选「模拟：低置信度需澄清」（不一定要真 LLM）。
5. **稀疏 / 零候选**：开关或第二套 `mockData` 稀疏模式 → **零结果页 / 单人套餐兜底** + 一句「已放宽距离」解释。
6. **并发叙事（轻量）**：Dev _TOGGLE 或脚注：`match_version`、`reservation_ttl` 文案，表示真实系统会有锁与幂等（不要求真分布式）。

### P2 — 与交互文档逐条对齐的 completeness

7. **地图**：Bottom Sheet 内 **加入这个局 / 我也想去** 与文档示例一致；**时间筛选**、**热度切换**若未实现则补。
8. **AI 成局助手**：方案对比表、**换一个时间/局**、**为什么推荐** 与 §5.5–5.6 一致。
9. **数据模型**：`active_plan_count`、`Trust Profile` 等字段在 mock 与 UI 上曝光（可与 Profile/确认室卡片一致）。

## 3. 分阶段里程碑（建议排期）

### 阶段 A — 状态机与交易叙事（约 2–4 个迭代日）

| 任务 | 验收标准 |
|------|----------|
| A1. 抽出 `planStatus` / `matchRoom` 状态枚举 | 聊天页顶部卡片与按钮随状态变化；代码中无魔术字符串散落 |
| A2. 双确改为可中断流程 | 「我确认」后进入 `waiting_partner`；对端确认可改为**按钮模拟**或**随机拒绝**演示 |
| A3. 预授权 / 诚意金面板 | 在 `confirmed` 前或进入成功页前插入一步；文案与 `demo-open-issues` §3 对齐 |
| A4. 更新 `demo-open-issues-and-architecture-gaps.md` | 将已闭环条目标记为完成或删除 |

### 阶段 B — 异常流与重规划扩展（约 2–3 个迭代日）

| 任务 | 验收标准 |
|------|----------|
| B1. `PARTNER_DECLINED` 事件 | 注入候补 `user`；或展示「切换无需排队商家」卡片 |
| B2. `EXIT_BEFORE_30MIN`（模拟） | 系统消息 + 「重启匹配 / 退款说明」Toast 或面板 |
| B3. 扩展 `replanMatch` 或并列 `replanPartner` | 与 `applyReplan` 统一为**事件驱动**，便于演示脚本 |

### 阶段 C — 稀疏与 AI 分层展示（约 1–2 个迭代日）

| 任务 | 验收标准 |
|------|----------|
| C1. `?sparse=1` 或 UI 开关 | `runMatching` 零结果时进入专用空态 + 单人 deal 推荐 |
| C2. AI 页「解析来源」 | 标签旁显示规则/可选澄清问题；可选 `setTimeout` 模拟 P99 加载条 |

### 阶段 D — 与《交互设计更新文档》§8 对表

| 任务 | 验收标准 |
|------|----------|
| D1. 自检表格 §8.1–8.3 | 每项打 ✅/⏳，剩余项进入 backlog |
| D2. 答辩彩排 | 口述主线：**成局地图 → AI 成局助手 → 成局确认室 → 到店转化**，并各补一句异常兜底 |

## 4. 建议改动的代码入口（当前仓库）

- `app.js`：`confirmMatch`、`renderChatPage`、`renderAIPage`、`renderSuccessPage`、导航与全局 `appState`。
- `utils/matching.js`：`parseIntent`、`runMatching`；可新增 `getAlternateMatch` / 澄清结构。
- `mockData.js`：候补用户队列、稀疏模式数据集、`active_plan_count`、`trust` 展示字段。

（若仓库根目录与 `docs/` 分离后引用路径变化，以实际 `index.html` 引用为准。）

## 5. 不建议在本阶段做的（避免范围爆炸）

- 真实微服务、分布式锁、真实支付接口。
- 完整 LLM 链路；答辩用 **规则 + 延迟/澄清模拟** 即可回应缺口文档。
- 照搬 MealMate 的关注/Feed/订单中台（交互文档 §7.1 已否定）。
