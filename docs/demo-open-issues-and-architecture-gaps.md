# Meituan Together Demo — 已知问题与架构缺口清单

本文档汇总当前 Demo 在 **产品叙事、基建与工程实现** 上的已知局限与待论证项，便于评审、排期与后续迭代对照。

---

## 执行摘要

| 维度 | 现状概要 | 风险等级（相对 Demo 目标） |
|------|----------|----------------------------|
| 意图 / AI | 规则同步解析，无真实 LLM 延迟与幻觉场景 | 高（接模型后体验与正确性未验证） |
| 并发 / 状态机 | 成局路径近似 Happy Path，无双边冲突与库存 | 高 |
| 交易 / 履约 | 展示团购结果页，无预授权、防鸽、退款契约 | 高 |
| 供给 / 稀疏性 | Mock 高密度商圈（三里屯式），无零候选降级 | 中 |

---

## 一、AI 与规则的边界

### 1.1 产品 / 架构层未回答的问题

1. **延迟**：地图场景下用户容忍度低；若 `parseIntent` 等关键链路依赖云端大模型，P99 达 1～2s 以上时的 **首屏策略、流式输出、可取消请求** 未在 Demo 中体现。
2. **幻觉与歧义**：例如「两杯美式」vs「两个人」、人数 vs 杯数、忌口与预算口语；缺少 **低置信度澄清、schema 校验、人在回路** 的交互与后端契约。
3. **分层缺失**：未区分 **L0 规则 / L1 小模型（本地或边缘意图）/ L2 云端大模型** 的职责边界与降级路径（何时不必调用 LLM、何时仅生成解释文案）。
4. **可观测性**：意图版本、模型版本、原始 query 存档、与最终成局字段的 **审计追溯** 未涉及。

### 1.2 与当前实现相关的具体缺口

- `utils/matching.js` 中 `parseIntent` 为 **同步正则**，与「真实 LLM 接入」后的行为 **不一致**；且难以表达细粒度槽位（杯数、人数、复杂否定等）。
- 无 **超时、重试、降级到规则/词典** 的 UI 或状态展示。

---

## 二、分布式并发与「库存」、成局状态机

### 2.1 产品 / 架构层未回答的问题

1. **抢占与锁**：同一优质搭子被多人同时匹配时，**预约占用（Reservation）**、锁粒度（用户 / 场次 / POI / SKU）、超时释放策略未定义。
2. **多边会话**：用户 A 确认 B 的同时，B 与 C **有限沟通**；需明确 **优先级、CAS 成局、失败一方的会话失效** 推送。
3. **POI / 券供给变更**：确认前卖光、涨价、打烊；确认后仍变更时的 **重校验、补偿、换店/退款** 未演示。
4. **幂等与乱序**：重复点击确认、网络重放、消息乱序下的 **幂等键与状态版本** 未体现。

### 2.2 与当前实现相关的具体缺口

- `app.js` 中 `confirmMatch()`：当前用户确认后，通过 **定时器在本地模拟** 对端立即确认并跳转成功页；**非**真实双边异步确认，也无冲突分支。
- 无双用户 **抢占、一方拒绝、会话过期** 等状态流转与 UI。
- `mockData.js` 中 POI 多为 `deal_available: true`、静态 `open_status`，无 **库存扣减、并发下单** 模拟。

---

## 三、履约与交易隔离（信任、支付、防鸽）

### 3.1 产品 / 架构层未回答的问题

1. **谁先付钱 / AA**：牵头人制、子订单、与美团支付/券体系的 **边界** 未产品化。
2. **防鸽与退款**：例如到店前一方取消，**诚意金/预授权冻结、极速退款、责任方、补偿券** 规则未闭环。
3. **成局契约**：成功页偏「社交成局」，缺少 **支付意愿锁定**（如：冻结诚意金、关联极速付、核销后解冻）的 **规则摘要与时间线**。
4. **动态重规划**：对端 **拒绝** 后，是否自动推 **候补搭子**、扩大召回或 **「低排队替代商家」**；当前仅有 **换店/等位** 类重规划，缺少「拒人→换人」策略演示。
5. **鸽 / 退局事件**：约定前 T-30min 退出时，**重启匹配、买单方极速退款路径** 未模拟。

### 3.2 与当前实现相关的具体缺口

- `renderSuccessPage` 等流程展示 **团购 deal**，无 **预授权 / 冻结 / 扣款状态机**。
- `confirmMatch` / 聊天内 **无**「对端拒绝」「候补 C」「退局触发」分支。
- `mockData.deals` 为静态展示数据，无 **支付失败、退款、核销** 状态。

---

## 四、双边市场冷启动与局部稀疏性

### 4.1 产品 / 架构层未回答的问题

1. **零或弱匹配**：方圆 N 公里、当前时段 **无候选** 时，是否 **放宽距离/时段/品类**、是否推荐 **单人套餐/官方组局**，以及如何 **解释召回策略** 避免「乱匹配」感。
2. **密度预期**：运营上多数 POI **非**核心商圈高密度；Demo 易因 Mock 产生 **供给充足的错觉**。
3. **冷启动**：新区域、新类目下 **种子用户/商家权益** 未讨论。

### 4.2 与当前实现相关的具体缺口

- `mockData.js`：`users`、`backgroundUsers`、`buddyDemands` **大批量同区生成**，地图上需求观感 **偏密**；无 **sparse（稀疏）数据集** 或「当前 3km 仅 N 人」的真实感展示。
- `utils/matching.js` 中 `runMatching` 虽有过滤阈值（如用户分 ≥50），但 **无**「零结果页」「单人兜底」的专用 UI 路径。

---

## 五、其他工程与演示层面问题

1. **Happy Path 主导**：主流程从匹配 → 聊天 → 双确 → 成功页，**异常与回退** 覆盖不足。
2. **重规划范围有限**：`replanMatch` / `applyReplan` 主要覆盖 **等位变化、换店**；与 `mockData.replanningEvents` 一致，**未覆盖拒人、鸽、支付失败**。
3. **高德地图**：`app.js` 使用可失败的外部 SDK；失败时有 toast，但 **与匹配/成局状态** 无联动。
4. **安全与合规**（略）：真实场景需另行补充 **未成年人、骚扰风控、隐私最小化** 等（Demo 未展开）。
